# Perforce workspaces

GitGud works on Perforce (P4) servers as well as Git repositories. Both
interfaces work the same way on either: the default UI stages, commits,
branches, and merges; the Depot UI works with pending changelists, check
out, and shelves. On a Perforce workspace every one of those runs a `p4`
command against your server.

GitGud drives the official `p4` command-line client, so install it first
(it comes with the Perforce client installers, or as a single `p4.exe`). GitGud
finds it on `PATH`, in `C:\Program Files\Perforce`, or wherever the
`GITGUD_P4` environment variable points.

## Setting up

- **First launch** asks whether new repositories should use Git or Perforce,
  and for your server (`P4PORT`, e.g. `ssl:perforce.example.com:1666`) and
  user. Change it later from *File ▸ Git or Perforce by default…* (default
  UI) or *Connection ▸ Git or Perforce by Default…* (Depot).
- **Set up a Perforce workspace** (the Perforce "clone"): the default UI's
  *Add ▸ Set up Perforce workspace…* (or *Clone repository…* when Perforce
  is the default), the Depot UI's *Connection ▸ New Perforce Workspace…*.
  Enter the server, user, a stream (`//project/main`) or, in a classic
  depot, a folder (`//depot/project/main`), and a local folder. *Find
  streams* lists the server's streams. GitGud creates the workspace (client
  spec), writes `.p4config` in its root, gets the files, and opens it.
- **Create a new stream** (the Perforce "new repository"): *Create new
  Perforce stream…*. GitGud creates the stream depot (this needs admin
  rights on the server) and a mainline stream, then a workspace for it.
- **Open an existing workspace**: any folder whose root has a `.p4config`
  naming the workspace opens like a repository (*Add existing repository or
  workspace…*). The file holds `P4PORT`, `P4USER`, `P4CLIENT`, and
  optionally `P4CHARSET`. Workspaces GitGud didn't create work too; add
  that file to their root.

GitGud always passes the server, user, and workspace to `p4` itself, so your
own `P4PORT`/`P4CLIENT` settings never redirect it. Set `P4CONFIG=.p4config`
in your environment and the `p4` command line uses the same file.

Workspaces GitGud creates use the `allwrite noclobber` options: every file
is writable, like a Git working tree, and getting latest never overwrites a
file you changed without opening it.

## Signing in

When the server asks for a password, GitGud asks once and saves it in the
Windows Credential Manager (`p4:<P4PORT>`). It logs in with `p4 login` and
keeps the ticket in memory; tickets you already have from the `p4` command
line work as they are. A refused password is removed and asked for again.
Unicode servers are detected and used with `P4CHARSET=utf8`.

## How Git ideas map

| In GitGud | On a Perforce workspace |
|---|---|
| Changed files (unstaged) | Files changed on disk but not opened (`p4 status`) |
| Stage / unstage | Open the file (`p4 reconcile`: edit, add, or delete) / `p4 revert -k` |
| Discard | `p4 revert` (opened files), get the have revision again (edits), remove (new files) |
| Commit | Submit (there are no local commits) |
| Push | Nothing to do: commit already submitted |
| Pull / fetch | Get latest (`p4 sync`, then a safe automatic resolve) / check the connection |
| Commit ids | Changelist numbers |
| History, file history | Submitted changelists (`p4 changes`, `p4 changes -i`) |
| Blame | `p4 annotate`, with lines you haven't submitted marked as such |
| Branches | Streams. In a classic depot, the folders next to the one the workspace maps (see below) |
| Switch branch | `p4 client -s -S <stream>` (or remap the folder), then get latest |
| Merge, squash merge, rebase | Integrate the other branch (`p4 merge`, `p4 integrate`), resolve, submit as one changelist |
| Revert a commit | `p4 undo`, submitted as a new changelist |
| Cherry-pick | Integrate one changelist from another branch |
| Tags | Labels (pinned to a changelist) |
| Stash | Shelved changelists (`p4 shelve`, then revert) |
| Worktrees | Your other workspaces of the same stream depot |
| Conflicts / merge tool | Pending resolves; the 3-pane tool shows base, yours, and theirs |
| Remotes | One: the server. Its address is editable |
| `.gitignore` | `.p4ignore` (GitGud sets `P4IGNORE=.p4ignore` when you haven't) |

A merge, revert, or cherry-pick that hits conflicts keeps its files in a
numbered changelist; resolve them, then commit (submit), or abort. Pulling
when a file you changed without opening it would be overwritten stops before
touching anything and names the files, as Git does: stage them and get
latest again, and the incoming changes merge.

**Classic depots.** A workspace that maps a folder, say
`//depot/project/main`, treats the folders beside it (`//depot/project/*`)
as branches: creating one copies the files there on the server (`p4
populate`), switching remaps the workspace. The branch root is
`GITGUD_BRANCHROOT` in `.p4config`.

**Not available on Perforce** (the commands are greyed out): staging part of
a file (Perforce opens whole files), amending or undoing a submitted
changelist, moving a branch back (reset), the reflog, interactive rebase,
renaming a stream, submodules, Git LFS, adding or removing remotes, and push.
Switching branches needs no open files: submit, shelve, or revert them first.

## The Depot UI on Perforce

On a Perforce workspace the Depot UI works with the server's changelists,
like any Perforce client:

- **Pending** lists the server's default and numbered changelists for this
  workspace, each file with its real action (edit, add, delete, move/add,
  integrate, locked). A file you edit without checking out isn't in a
  changelist until you **check it out** or use *Actions ▸ Reconcile Offline
  Work…*.
- **Check Out**, **Mark for Add**, **Mark for Delete**, **Rename/Move**,
  **Revert**, **Revert Unchanged Files**, **Lock** / **Unlock** are `p4 edit`,
  `add`, `delete`, `move`, `revert`, `revert -a`, `lock` / `unlock`.
- **Move to Changelist**, dragging files, and **New / Edit / Delete Pending
  Changelist** change the changelists on the server (`p4 reopen`, `p4 change`).
- **Submit** submits the changelist with the files you leave checked; the
  unchecked ones move to the default changelist.
- **Shelve** shelves on the server (`p4 shelve`), so everyone can see it;
  shelving the default changelist makes a numbered one first. **Unshelve**
  and **Delete Shelved Files** work on any shelf, and *Show changelists: All
  users* lists other people's.
- **Get Latest** and **Get Revision** are `p4 sync` (a changelist number,
  `#rev`, a label, or `none`). Files you changed without opening are left
  alone and listed in the Log.
- The depot tree shows real depot paths and marks files that are out of date
  (a newer head revision than you have). The Log lists the `p4` commands.

The Depot UI on a Git repository is unchanged: its changelists and shelves
still work as described in [Using the Depot UI](DEPOT.md).

## Troubleshooting

- *The p4 command-line client was not found*: install it, or set
  `GITGUD_P4` to the full path of `p4.exe`.
- *SSL certificate not trusted*: run `p4 -p ssl:host:port trust` once, or
  call `gitgud.p4Trust(port)` from the console.
- *Workspace 'x' doesn't exist*: the `.p4config` names a workspace the
  server doesn't have (deleted, or another server).
- Everything GitGud ran is in the console pane (default UI) or the Log
  (Depot), with the server's own messages.

## For developers

### How it fits together

```
Lua (gitgud.*)  ->  git::Repository  ->  libgit2            (a Git repository)
                                     ->  p4::P4Workspace  ->  p4 -G ...  (a Perforce workspace)
```

- **`git::Repository`** (`src/git/Repository.h`) stays the only type the rest
  of the app uses. `Repository::Open` checks the folder: a `.git` opens with
  libgit2; a `.p4config` naming `P4CLIENT` (and no `.git`) creates a
  `p4::P4Workspace`, and every public method then starts with
  `if (m_pP4) { return m_pP4->Method(...); }`. Worker jobs open their own
  `Repository` by path, so they get the backend too. `Backend()` says which,
  `Supports(feature)` what it can do (the list is in `Repository.cpp`).
- **`p4::P4Command`** (`src/p4/P4Command.*`) runs `p4 -G`: results come back
  as Python-marshal dictionaries, binary-safe and with multi-line fields
  intact, and specs go back the same way with `-G <spec> -i`. It always
  passes `-p -u -c -C -d`, handles the login retry (asking a
  `PasswordProvider`, then `p4 login -p` for a ticket kept in memory), and
  retries with `-C utf8` on unicode servers. Commands block: the UI thread
  runs the quick ones like it runs libgit2; network-sized ones (get latest,
  creating workspaces, listing streams) run on the `TaskRunner`.
- **`p4::P4Workspace`** implements the `Repository` API, split by topic:
  `P4Workspace.cpp` (plumbing, `.p4config`, status, opening files, submit,
  config, sync), `P4WorkspaceHistory.cpp` (changes, describe diffs, annotate,
  tree browsing, revision graph from `filelog`, conflicts),
  `P4WorkspaceBranches.cpp` (streams and folder branches, labels, merges,
  undo, cherry-pick, shelves as stash, workspaces as worktrees), and
  `P4WorkspaceChanges.cpp` (server changelists for the Depot UI). Paths
  cross the API workspace-relative (`src/a.cpp`); `LocalArg` turns them into
  escaped local paths for `p4`, `RelativeFromDepot` maps depot paths back
  through the client view. Diffs and 3-way merges reuse the Git layer's
  buffer helpers (`DiffFileVersions`, `ConflictFromBuffers`, `MergeBuffers`
  in `LibGit2Internal.h`), so P4 diffs look exactly like Git ones.
- **Lua**: `src/lua/LuaP4Bindings.cpp` adds `gitgud.backend()`,
  `gitgud.supports()`, and the `gitgud.p4*` calls ([Lua API](LUA_API.md)).
  `resources/scripts/core/p4setup.lua` holds the shared setup and sign-in
  dialogs. The Depot UI's `depot/changelists.lua` and `depot/actions.lua`
  return a proxy that hands calls to `depot/p4changelists.lua` and
  `depot/p4actions.lua` on a Perforce workspace; the Git code in those
  files is untouched.

### Adding to the Repository API

Every new public `Repository` method needs a Perforce side: add it to
`P4Workspace`, forward it at the top of the Git implementation, and either
implement it with `p4` or throw through `Unsupported("What it is")` and add
a `Supports()` feature name so the interfaces can grey it out. Check `p4`'s
tagged output first (`p4 -G <command>` against a test server); field names
are more stable than its text messages.

### Testing

- `tests/test_p4.cpp` runs against a real, throwaway server. Set
  `GITGUD_TEST_P4D` to `p4d.exe` and `GITGUD_P4` to `p4.exe` (both from
  Perforce's downloads; the free server needs no license for a few users).
  Each test starts p4d in `rsh` mode (p4 launches it per command; nothing
  listens on a port) in a temp folder with its own tickets file. Without the
  variables those tests skip, so CI runs only the marshal tests.
- `tests/ui/make-p4workspace.ps1 -Dir <scratch> -P4 <p4.exe> -P4D <p4d.exe>`
  makes a server and workspace for the UI harness; it prints the
  environment to launch with (a scratch `P4TICKETS`, so the Credential
  Manager isn't involved). `tests/ui/p4.lua` (default UI) and
  `tests/ui/depot-p4.lua` (Depot UI) drive the real interface on it, the
  same way as the other scripts in `tests/ui/`.

### Known gaps and next steps

- Status runs `p4 status` over the whole workspace on each refresh, which is
  slow on very large workspaces; a cached or folder-scoped status would help.
- Pull and branch switching refuse rather than carry unopened edits along;
  switching could shelve and unshelve open files automatically.
- The commit graph links each stream's changes in order but doesn't draw
  integration edges between streams (the file revision graph does).
- Not tried yet against: SSL servers, edge/commit server setups, streams
  deeper than one level (`StreamDepth` beyond `//depot/1`), virtual and task
  streams, and very large workspaces.
